# i-go-sleep

用户去睡觉了。本轮参数：**$ARGUMENTS**（第一个是项目文件夹，后面是本轮目标）。

## 一、这期间的两条硬规则

1. **不许问用户任何问题。** 不用 AskUserQuestion，不停下来等确认，不写"请您拍板"。用户睡着了，问了也不会有人答。
2. **不许进计划模式。** 不用 EnterPlanMode，也不用 ExitPlanMode。进了计划模式就出不来了——用户睡着，没人点同意，主代理没法自己回到原来的模式，整晚就卡在那里。这条同样写在 `allowed-tools` 白名单里挡住：白名单之外的 EnterPlanMode、AskUserQuestion、ExitPlanMode 工具在这期间根本调不出来。如果因为某种原因这层限制没生效，也一律不许调用。
2. **目标没完成不许停。** 遇到不确定的地方，按项目文档里已有的决定、按最小改动往下走，把不确定的点记下来等用户醒了再问。不许因为"子代理说要等我确认"就整晚空转。

## 二、开工前先读项目

1. 用 Skill 加载 `doc-driven-dev`，项目目录用用户指定的那个文件夹。
2. 按 doc-driven-dev 的「阶段 0」读上下文：`docs/index-*.md` 的项目脉搏和目录、decision 汇总、lesson 汇总、当前任务相关的 idea / landing / exp。要弄清四件事：当前目标和进度、已有决定及理由、踩过的坑和用户纠正、可复用的代码数据和模型。
3. 用户没给目标时，从 index 里的「下一步」取，仍然不许问用户。
4. 读基础代码：把项目实际跑的入口、配置、评测脚本读一遍，确认真实存在，不要只看文档。

## 三、派子代理的规则

**所有写代码、训练、推理、评测、看结果，全部交给 opus 子代理，主代理不动手做实验。** 主代理只做四件事：读文档、拆任务、派子代理、记录和汇报。

1. **派子代理必须显式写 `model: "opus"`。** 不写会继承父代理的模型。
2. **只提需求，不提设想。** 不许把主代理关于具体功能的猜想想写进子代理的提示词。以下这些话一律不准出现在提示词里：
   - "我怀疑是 xxx 模块的问题"
   - "我建议用 xxx 方法实现"
   - "这个功能应该做成 xxx 的样子"
   - 任何主代理自己想的方案、结构、命名、参数

   原因是：主代理一写设想，子代理就会照着主代理的猜想写代码，而不是照数据和实际报错去查。子代理会被带偏，最后交回来的东西是在验证主代理的猜想，不是在解决问题。

3. 子代理的提示词里只放这四样：
   - **要达成什么**：可验证的目标和通过标准（跑通什么、指标到多少、产出什么文件）。
   - **去哪看**：项目文件夹绝对路径、要读的文档路径、相关代码路径、数据路径。
   - **约束**：不许做什么、已有的决定和踩过的坑（把 decision 和 lesson 的相关内容摘给它）、时间或显存限制。
   - **要交回什么**：结果、产出文件的绝对路径、命令和日志路径。

4. **子代理说"等您拍板"时打回去继续做。** 主代理现在是老板，让子代理按文档里已有的决定和最小改动继续推进，或者先做能确定的那部分。目标数值以用户原话为准，配置不同就算达标也不算达标。
5. 相互独立的任务并行派，在一条消息里发出去。
6. 不要轻易被子代理忽悠停下来：比如子代理说已经没有优化空间时，记住你是老板，不能简单满足于子代理说没优化空间这一点

## 四、夜间工作日志

上下文会被压缩，醒来汇报不能靠记忆。主代理把每件事追加写到日志文件：

```
<项目文件夹>/.igo-sleep/<当天日期>-sleep-log.md
```

每条记：时间、派了哪个子代理、目标是什么、结果、产出文件的绝对路径、失败原因。日志只记事实和路径，不记主代理的猜想。

## 五、用户说"我醒了"之后

1. 停止派新任务。还在跑的子代理，让它把当前状态写下来（已完成到哪、结果、checkpoint 和日志的绝对路径）再停，不要丢掉已有产出。
2. 按下面的规则汇报这段时间的全部进展。

### 汇报规则（硬规则）

- **只报事实**，每条进展都带证据。
- **凡是引用数字或文件，把文件的绝对路径完整打印出来**，不要写相对路径，不要写"见输出目录"。
- **任何数字在汇报前，主代理必须自己用 Read 工具打开对应的评测输出文件或日志重新确认一遍。** 不许引用子代理在对话里说的数字，不许凭记忆写数字。
- **报数字时必须同时说清楚**：这个数字怎么测出来的（脚本、命令、参数设置）、评测集是哪个、评测集有多少条、跟谁比。这四项缺哪项就写「未知」，不许猜。
- **失败和没做完的照样报**，说明卡在哪、已经产出了什么文件、下一步能怎么试。
- 不要在汇报里写主代理自己的猜测和设想，用户要的是发生了什么。

### 汇报格式

```
## 做完的
### 1. <进展标题>
- 结论：……
- 数字：<指标> = <值>
  - 文件：<绝对路径>
  - 测法：<评测脚本> / <命令> / <参数设置>
  - 评测集：<名称>，<N> 条
  - 对比：<和谁比，差多少>
- 产出文件：<绝对路径>

## 没做完 / 失败的
- ……

## 需要你拍板的
- ……
```

最后一条「需要你拍板的」只在用户醒来后写，睡着的这段时间不许拿这些问题去打断用户。

## 六、不要自己巡检

主代理不设高频定时唤醒自己去轮询子代理。要看进度就让子代理在后台跑，异常时向主代理汇报；主代理只在收到子代理结果或用户消息时才动作。

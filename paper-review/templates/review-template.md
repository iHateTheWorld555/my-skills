# 方法

核心原则：**内容覆盖遵循原文，讲解顺序遵循概念依赖和因果链。** 不要机械照搬论文目录，也不要在没有必要时强行改写成单一数据流。

动笔前先列出方法中的对象、数据/监督、训练阶段、损失、推理组件和评估诊断，并检查每个概念是否在首次使用前已经定义。若原文顺序本身连贯，可沿用；若原文在正文与附录之间交叉介绍任务定义、数据、训练、推理或指标，则应重组为读者能够顺序理解的结构。

推荐依赖顺序：任务定义 → 理论推导或 toy experiment →  数据管线 → 模型架构 → 方法管线 → 训练与推理管线 → 实验细节与实验结论。

## 技术章节覆盖范围

需要覆盖原文中所有包含实质技术内容的章节，不限于名为 Method的部分，例如：

* Method / Approach / Model / Framework
* Data / Dataset / Data Pipeline
* Training / Optimization / Alignment
* Inference / Sampling
* System / Architecture / Implementation
* Benchmark / Evaluation Protocol
* Appendix 中的重要实现细节

不要遗漏关键技术内容，也不要把纯背景或实验结果当作方法来讲。

## 小节讲解方式

以一个完整功能阶段作为小节，而不是以论文页码或 Appendix 编号作为小节。可以合并原文中分散但属于同一机制的正文、数据和附录内容，并在必要时括号标明来源章节，确保覆盖可追溯。

对于每个阶段，重点讲清楚：

### [功能阶段或机制名称]

* 它为什么出现在前一阶段之后，解决哪一个尚未解决的问题。
* 它消费什么数据、监督或上游表示，并产生什么供下一阶段使用的结果。
* 核心流程按真实依赖顺序说明；适合步骤化时用有序列表，否则使用连贯段落。
* 哪些组件只在训练时存在，哪些保留到推理，哪些只是评估诊断。
* 原文给出的重要实现信息（如数据规模、训练设置、参数等）。

>🔍 注意：
> - 不要让读者先看到未定义的 anchor、teacher target、loss 或数据集，到后面才补来源。
> - 不要为了形式统一，重复写缺乏信息量的“做什么/输入/输出”条目；连贯性优先于模板外观。
> - 如果某些关键细节原文没有说明，可以简单指出"原文未说明"，不要自行补充。
> - 如有数学符号，用内联公式包裹，不允许使用代码块包裹；如有较长的数学表达式，使用公式块表示

# 限制

不要只复述作者在Limitations 章节中承认的问题，也不要为了凑数量写泛泛而谈的缺点。请从以下七个角度主动审查这篇论文的潜在限制，判断这些限制是否会影响论文的科学价值、方法价值或社区价值，并只总结最关键的限制，限制本身必须简短而清晰，不要逐个按点硬凑限制，一行一个限制即可

请优先分析真正影响论文可信度的限制，不要写"未来可以扩大数据集""未来可以优化效率"这种无信息量表述。

## 1. 对象限制：论文研究的问题是否真实、清楚、值得研究

检查论文提出的问题、任务、能力、机制或评价维度是否真实存在，是否被清楚定义，是否具有足够的研究价值。

重点判断：
* 论文的核心问题是否只是作者人为发明出来的概念。
* 核心概念是否可以被操作化定义。
* 指标是否真的对应作者想解决的问题，还是只是 proxy偷换。
* 论文 claim 的范围是否超过了实验验证范围。
* 如果是 benchmark、数据集、系统或问题定义论文，场景是否真实，是否有社区价值。
* 这个问题是否可能已经被简单方法、已有方法组合或先前工作基本解决。

## 2. 识别限制：论文是否真的证明了"为什么有效"

检查论文是否识别了真正带来提升的原因，而不是只展示结果变好。

重点判断：
* 是否有最简baseline，是否有和一个明显更简单的方法比较
* 是否有强baseline 和最近SOTA。
* 是否隔离了关键变量。
* 是否同时改变了模型结构、数据、训练步数、推理策略，却把提升归因于某个单一模块。
* 是否有充分消融支持核心 claim。
* 外部工具、后处理、额外数据、额外推理计算是否偷走了主要贡献。
* 比较是否公平，例如同backbone、同数据、同 compute、同推理预算。

## 3. 独立性限制：证据是否和结论构造过程形成闭环

检查训练、筛选、标注、评测之间是否相互污染，导致证据不独立。

重点判断：
* reward 和 evaluation 是否重叠。
* 数据生成、数据筛选和最终评测是否来自同一个模型或同一类偏好源。
* synthetic data 是否有独立的人类校验。
* judge是否被污染，是否只是测"像某个闭源模型"的程度。
* benchmark 是否有独立可信的评测锚点。
* 评测时是否使用了部署阶段不可得的信息。
* 最终结论是否依赖一个训练—筛选—评测闭环。

## 4. 压缩限制：方法是否过度复杂，解释力是否不足

检查论文是否用过多模块、过多假设或过多工程技巧换取有限提升。

重点判断：
* 方法是否只是多个已有模块的工程拼接。
* 复杂模块是否都有必要性证明。
* 是否存在命名膨胀，把标准做法包装成新概念。
* 是否提出了真正的问题重构、机制解释、统一视角、规律发现或trade-off 分析。
* 复杂方法是否明显优于简单 heuristic。
* 方法是否能解释更多现象，还是只在当前设置下调参有效。
* 如果删掉某些模块，性能是否仍然接近。

## 5. 效用限制：效果是否真的达到可用或有意义的水平

检查论文结果是否在绝对效果、相对提升、指标覆盖和baseline 可靠性上站得住。

重点判断：
*绝对指标是否达到领域内可用水平。
* 相对提升是否足够大，还是只是统计上或数值上小幅提升。
* 提升是否广泛存在于主要数据集、主要任务和核心指标上。
* 是否只在少数指标、少数设置或弱 baseline 上取胜。
* 是否大量核心指标输给baseline，但作者只强调少数赢的指标。
* 如果存在 trade-off，作者是否诚实讨论。
* 对benchmark 论文，评测指标是否可信，baseline覆盖是否充分。
* 对问题定义论文，是否证明该问题广泛存在且值得解决。
* 对分析论文，现象是否稳定、可迁移，而不是偶然观察。

## 6. 新颖性限制：创新是否是真实增量

检查论文所谓创新是否只是已有方法的换名、拼装或跨领域搬运。

重点判断：
* 核心 idea 是否已经在本领域出现过。
* 是否只是把A + B + C 拼起来。
* 是否只是从其他领域迁移过来，但没有证明迁移后解决了本领域真实问题。
* 每个新增组件是否都有必要性实验。
* 组件之间是否存在 synergy，而不是简单相加。
* 是否有新的机制解释、问题重构、经验规律或理论视角。
* 论文声称first、new、unified、general、foundation 时，是否真的成立。

## 7. 可复现限制：别人是否能独立验证论文结果

检查论文是否提供足够信息让他人复现实验结论。

重点判断：
* 代码是否开源。
* 数据是否可获取。
* 模型 checkpoint 是否可用。
* 训练细节是否充分，包括 batch size、学习率、优化器、训练步数、数据配比、硬件规模等。
* 评测脚本是否公开。
* prompt、filtering rule、preprocessing、postprocessing 是否清楚。
* 是否依赖闭源 API、闭源 judge、闭源数据或不可公开的人工标注。
* 如果依赖闭源组件，是否有独立验证或替代实验。
* benchmark 是否可以被社区稳定复用。

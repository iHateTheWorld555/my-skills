# doc-driven-dev

项目或动作：**$ARGUMENTS**

## 基本规则

1. 行动前读取项目文档，行动后更新文档。
2. 所有文档创建、更新、实验日志追加、时间戳、索引和交叉引用都通过 `docdev` 完成。不要直接编辑 CLI 生成的 Markdown。
3. Agent 通常只向 CLI 提交 `content`；`title` 可省略。文件名、路径、格式、时间、landing revision 和索引由 CLI 处理。
4. 正文用 `[[文档 ID]]` 或 `[[文档 ID|显示名称]]` 建立交叉引用。写入前先用 `docdev search` 找到目标 ID，CLI 负责验证和生成相对链接。`docdev board` 把整个引用网络渲染成 `docs/board.md` 看板。
5. 同一事实只详细定义一次：数据集、模型和流水线放在对应 landing，其他文档只引用。
6. 正式同步顺序为 exp → decision → lesson → landing → index。index 最后更新，且只写当前焦点。
7. 读文档用 `docdev read <id>` 而非直接读文件；连续 5 个**活跃日**（实际用过 docdev 的日期，不是自然日）未读的 exp/decision/lesson 会被自动归档到 `docs/archive/`（可用 `docdev unarchive` 恢复）。长期不干活不会触发归档。
8. CLI 命令失败时先修正输入或运行 `docdev validate`；不得绕过 CLI 手工修补格式。

CLI 完整字段和示例位于 `references/cli-contract.md`。使用 Skill 加载时显示的 base directory 定位 `bin/docdev`；若执行过 `install.sh`，也可直接调用 PATH 中的 `docdev`。

## 初始化

项目没有 V3 文档系统时运行：

```bash
<skill-base>/bin/docdev init <project-dir> --name <project-name>
```

初始化会建立固定项目目录、项目 index、dataset/model/pipeline 三份 landing，以及 `.gitignore`。文档和 assets 默认不进入 Git。

## 文档生成铁律（控制文档膨胀）

**只在两种时刻写文档**：
1. **有里程碑进度** —— 实验出关键结果、定案、收口、范式转向；
2. **发现导致严重损失的问题** —— 踩坑、数据泄漏、评测口径错、会重复犯的错。

其余琐碎过程（中间测量、临时调试、无关紧要的调整）**不写文档**。

**每天最多新增 5 篇文档**：超过当日上限不再新建，改合并进已有文档。

**同类不新建**：先 `docdev search` 找已有聚合文档，用 `docdev doc --id` 更新/追加，
不另开新篇。一个研究方向只保留一篇活跃 exp/decision/lesson，后续结果追加进去。

**术语白话化**：首次用到黑话必须给白话解释；项目级术语表见
`idea-术语表`（用 `docdev search "术语表"` 找），正文里引用它而不是重复解释。

## 文档写作规范（写文档必须按此模板）

| 类型 | 必写内容 | 禁止 |
|---|---|---|
| **exp** | ①探究目标 ②对应探究分支 ③训练/推理/评测文件路径 ④实验结果（关键数字） ⑤简单结论。**题目直接写是否为正向改动**（`exp-日期-<正向\|负向\|证伪>-<名>`）；同组扫参实验用一个文档；eval 实验不单独写文档（结果归入所属 exp） | 中间推导、过程记录、运行日志 |
| **decision** | 决策内容本身（结论、配置、撤销） | **不写为什么**（动机、推导、证据链） |
| **lesson** | ①犯错内容 ②如何修改 | 现象细节堆砌、根因推导、外部旁证 |
| **idea** | 研究问题、假设、当前结论 | 调研过程、验证计划、中间结果 |
| **landing** | 稳定事实（路径、格式、参数、入口） | 历史演变 |

- 目标：**每篇 ≤1000 token**。写不下的细节不写，不是塞进去。
- **术语白话化**：首次出现黑话必须给白话解释；项目术语表见 `idea-术语表`
  （`docdev search "术语表"` 找），正文引用它而非重复定义。

## 文档内容分流

Agent 只判断内容属于哪类，不维护模板或固定小节：

- `index`：当前在做的实验与 idea、阻塞和下一步。保持简短，不写文档目录（清单直接 `ls docs/*`）。
- `idea`：研究问题、假设、动机、最小验证想法和当前结论。
- dataset landing：数据路径、格式、统计、切分、预处理和数据版本。
- model landing：模型结构、参数、关键模块和预训练权重。
- pipeline landing：预处理、训练、推理、评测的入口、顺序和使用方法。
- `exp`：实验目标、baseline、指标、运行记录、模型输出、失败案例和结论。
- `decision`：技术选择、方向否决、用户批评及其证据和影响。
- `lesson`：踩坑或用户纠正，重点写清现象、根因、正确做法和复发信号。

这些只是内容边界，不是必填 slot。调用 `docdev doc <type>` 时正文 `content` 是唯一必填信息。

## 阶段 0：读取上下文并定位当前阶段

1. 先列目录看清有哪些文档，**文件名即标题**，不需要读任何索引：
   ```bash
   ls docs/ideas docs/landing docs/exps docs/decisions docs/lessons
   ```
   长期未读（超过 5 个活跃日）的实验/决策/经验在 `docs/archive/` 下，需要时再看。
2. 读 `docs/index-*.md` 了解当前焦点（在做哪个实验、哪个 idea、阻塞、下一步）。它很短，不含目录。
3. 从文件名判断哪些 decision 与 lesson 与当前任务相关，避免推翻已有决定或重复踩坑。
4. **读正文一律用 `docdev read <id>`，不要直接读 Markdown 文件**：它会刷新未读计时，
   否则文档在 5 个活跃日后会被自动归档。按内容查找用 `docdev search`（默认只返回 ID、类型、标题和更新时间；
   需要片段与引用列表时加 `--verbose`）。
5. 需要看清文档之间的引用关系、孤立文档或实验活跃度时，运行 `docdev board` 并读取 `docs/board.md`；需要交互式浏览、编辑或删除时，用 `scripts/docboard_server.py` 起看板服务。
6. 提取四项上下文；缺失时标记为“未知”，不得假设：
   - 当前目标和进度；
   - 已有决定及理由；
   - 已踩过的坑和用户纠正；
   - 可复用的代码、数据、模型和流水线。
7. 文档与代码或实验产物冲突时，以当前可验证事实为准，并通过 CLI 更新 lesson、landing 或 exp。

根据用户已有内容，以及用户的指令选择切入点：

| 用户已有内容 | 切入阶段 |
|---|---|
| 想法或方向 | 阶段 1 |
| 已有方案，需要落地 | 阶段 2 |
| 已有代码，需要实现或修复 | 阶段 3 |
| 代码就绪，尚未试跑 | 阶段 4 |
| 实验正在运行 | 阶段 5 |
| 实验已停止，需要结论 | 阶段 6 |

> 当用户已经明确告诉你它的需求时，优先根据用户的需求判断当前阶段

## 阶段 1：调研

1. 将目标拆成明确子问题。
2. 先检查项目内已有实现、decision、lesson 和历史 exp。
3. 对外检索先搜索 GitHub，并按 Star 数优先；再通过 arxiv、deepxiv 等搜索高影响力与强相关论文。
4. 独立、可并行或阅读量大的子问题可交给子代理。任务必须带上相关路径、decision、lesson 和项目上下文摘要。
5. 调研形成新研究假设时，通过 `docdev doc idea` 创建 idea。

## 阶段 2：规划与实验登记

1. 明确本轮假设、baseline、主指标和要修改的模块。
2. 创建或更新 idea。
3. 通过 `docdev doc exp` 创建本轮 exp；后续阶段的实验记录都归入该 exp。
4. 真正独立的实现或调研才并行分派；小任务由主代理直接完成。
5. 子代理看不到主对话，委派时传入完整目标、约束和相关文档摘要。不要重复执行已经委派的同一工作。

## 阶段 3：编码

1. 分析所需的基础功能，并检查是否已有流行的开源实现可以直接复用，这可以保证代码可靠的同时并加快实现。
2. 完成第一版基础实现后必须交给独立代理交叉 review，再根据确认的问题修改。只有 `src/dashboard` 可视化代码和明确的一次性临时脚本可以跳过交叉 review；模型、模块、训练、推理、预处理、评测和通用工具代码都不能跳过。
3. 在不改变研究逻辑的前提下调研并应用合适的效率优化：
   - 优先使用成熟的高 Star 加速库、融合算子、`torch.compile` 或混合精度，而不是自行重写内核；
   - 对结果可复用的重复计算做缓存；
   - 评测和推理尽量批量执行，在可控范围内提高 batch size 以利用显存和吞吐量；
   - 多卡评测或推理优先按样本做静态分片，各卡独立处理后汇总结果；
   - 只有用户明确要求性能调优时，或已有证据无法定位瓶颈时，才用 profiler 采样分析，不在普通训练中持续开启 profiler。
4. 先运行快速单元测试和数据测试：
   - 快速单元测试：本次修改涉及的 shape、dtype、device、关键输出、不变量及 NaN/Inf；
   - 数据测试：读取、字段、shape、dtype、值域、标签、切分、预处理及样本到模型的链路。
5. 第三类测试——小样本 train 过拟合——统一在阶段 4 执行。
6. 同一错误连续修改两次仍未解决时，联网搜索已有解法，不继续盲试。有效解法进入待记录 lesson。

保持既定源码目录：`src/model`、`src/modules`、`src/train`、`src/infer`、`src/preprocess`、`src/eval`、`src/util`、`src/dashboard`。项目根目录只使用初始化生成的 8 个顶层目录，源码放在上述 `src/` 子目录中。

## 阶段 4：smoke test

1. 使用一小批数据训练至少 50 步。
2. loss 有明显下降趋势才允许进入正式训练。
3. 失败时回到阶段 3。
4. 先把有复用价值的诊断内容通过 `docdev doc lesson` 保存。
5. 再运行 `docdev clean --dry-run` 检查候选目录，随后运行 `docdev clean` 删除 `exp/` 下名称含 `smoke` 或 `debug` 的实验目录，避免污染看板。

## 阶段 5：正式训练与监控

1. 主动说明训练配置并与用户确认；用户已明确配置且要求不再询问时直接使用。
2. 启动实验时把完整配置快照到实验目录。
3. 默认不设置最大训练步数；只有学习率调度等实现确实依赖总步数时才设置。
4. 使用 `docdev doc exp --id <exp-id> --append` 轻量追加子实验日志，不在训练中频繁写正式结论。
5. 监控节奏固定为：启动 2 分钟后检查第一次；再过 2 分钟检查第二次；均正常后每 60 分钟检查一次。
6. 检查训练进程、loss、grad norm、显存、吞吐量、数据加载、日志和 checkpoint。可以记录裁剪前 grad norm，但不使用跨模型固定健康阈值。
7. 有空余节点时可用固定的 100–200 条代理评测子集追踪指标，保持简单。

## 阶段 6：停止与结论

训练没有默认最大步数。根据当前任务、训练曲线、baseline、代理评测、资源和用户决定判断是否停止，不使用统一固定阈值代替研究判断。

停止后形成三种结论之一：

- 超过 baseline：进入阶段 7；
- 训练健康但未超过 baseline：记录负结果，阶段 7 后回退阶段 1；
- 资源耗尽：记录现有证据并终止。

失败案例必须查看模型输出本身，不能只引用指标数字。

## 阶段 7：集中同步

一轮实验结束、发生回退前或用户纠正时：

1. 更新 exp：关键发现、最佳指标、失败案例、继续/放弃/合并结论和日志明细。
2. 有技术选择、方向否决或用户批评时创建 decision。
3. 把踩坑和用户纠正创建为 lesson，必须写清复发信号。
4. 数据集、模型或流水线的固定事实变化时更新 landing；CLI 自动维护 revision。
5. 最后更新 index：只写当前在做的实验与 idea、阻塞和下一步，保持简短。
6. 运行 `docdev validate`。
7. 运行 `docdev board` 刷新看板，确认引用网络里没有意外的孤立文档。
8. 运行 `docdev archive`（不带 `--apply` 只看候选）确认没有还需要的文档被判为到期；确实不用了再 `--apply`。
9. 执行常规 Git 提交时不需要再次询问用户，但不得提交 docs、assets、数据、权重、实验产物或凭据。

## 回退规则

异常先形成候选原因并做最小诊断，不把症状直接等同于根因：

| 异常信号 | 优先排查 | 通常回退到 |
|---|---|---|
| shape 错、精度异常、NaN/Inf | 实现、数据、数值和配置 | 阶段 3 |
| loss 尖峰、梯度异常、OOM | 配置、数据、实现和资源 | 阶段 3 或阶段 5 |
| 训练健康但不超过 baseline | 研究假设 | 阶段 1 |
| 小样本 50 步 loss 不明显下降 | 训练链路、数据、目标或实现 | 阶段 3 |
| 资源耗尽且无有效信号 | 方向或资源条件 | 阶段 7 后终止 |

回退前先同步 exp 和 lesson；记录触发信号、证据、判断、目标阶段和要修改的内容。同一判断连续回退两次仍无效时交给用户重新判断。回到阶段 1 或阶段 3 后必须重新通过阶段 4。失败配置和负结果不得清空。
